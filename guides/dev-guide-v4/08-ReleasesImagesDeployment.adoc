
[#releases-images-and-deployment]
== Releases, images and deployment

Nobody assembles a release of Niord by hand. Every merge to the main branch that changes code and whose
checks all pass is published as a new version, and the countries take the versions they want from
there. The workflow that does it is `.github/workflows/publish.yml`; `be/docs/cicd/intended-use.md`
explains the whole path from a change to a running deployment in plain words.

The publication starts when the checks of a push to `main` finish. A merge that changes only
documentation, such as the guides of this site under `guides/`, the backend's documents under
`be/docs/` or the records under `docs/`, starts no checks on `main`, so it publishes nothing; its
change is carried by the next version a code merge publishes.

[#what-a-release-is]
=== What a release consists of

A release is a version number, `4.0.<n>`, where `<n>` is the number of the publication run. One
version covers the whole base product, backend and frontend together, so a backend and a frontend
that were never tested together cannot be combined. A version is published only when every check
that ran for its commit on `main` passed; a red check publishes nothing. There is one exception, for
an emergency: a maintainer can start the publication by hand on `main`, and that run publishes after
the backend's unit tests alone, while the integration tests run and report afterwards. Such a run is
labelled as one in its name and summary, and it is not for routine use.

Each version publishes:

[cols="40,60",options="header"]
|===
|Artifact |What it is

|`org.niord:niord-parent`
|The parent POM a country's backend inherits: the dependency versions the library was tested with
 and the test configuration.

|`org.niord.base:niord-base`, with its test-jar
|The backend library, and the test harness a country's tests use.

|`org.niord:niord-bootstrap` (zip)
|The base product's bootstrap (<<the-bootstrap>>).

|`org.niord.web:niord-web-admin` (zip, classifier `en`)
|The production build of the generic administration application.

|`org.niord.web:niord-fe-src` (zip)
|The base product's frontend sources, which a country's set-up builds from.

|`org.niord:niord-country-kit` (zip)
|The country kit, with its guides and the backend contract.

|`org.niord:niord-image-tools` (zip)
|The scripts that build a backend image and check a country's jar.

|`org.niord:niord-local-run` (zip)
|What a country's `start-local.sh` needs for a local run: the launcher library, the compose file,
 the local realm and the sample content. It holds known passwords and is for a local run only.

|The image `niord/niord-app-en`
|The container image of the generic application (<<the-images>>).

|The Helm chart `niord`
|The chart that deploys a stack (<<the-helm-chart>>), with the same version as the application.
|===

The Maven artifacts go to the GitHub Packages registry of the NiordOrg organisation, the image
and the chart to the project's container registry. The commit is then tagged `v4.0.<n>`, and a
release on that tag records the SHA-256 checksums of the source zip and the kit package, which a
country pins. Before anything is published, a check makes sure that the backend's jars, the
bootstrap zip and the inputs of the image carry nothing of the sample content; `niord-local-run` is
the one artifact that carries the sample, on purpose, for a local run.

A published version can be withdrawn with the workflow `.github/workflows/retract-version.yml`. It
removes the version's Maven artifacts, its release and its tag; the image and the chart in the
container registry it only lists, and they are deleted there by hand. A country that pinned the
version is then told to move on. While the workflow's environment holds no token to delete the
Maven artifacts with, a run is refused before anything is removed.

[#the-images]
=== The images

*The backend image* is built from `be/k8s/docker/Dockerfile`, one image per deployable: the
generic one here, and each country's in its own repository from the same scripts. The image runs
the application on Java 25 as an unprivileged user and listens on port 8888. Its layers are ordered
so that the parts that rarely change are stored once: the Java runtime, then the third-party
libraries (built to be the same bytes on every build), then `niord-base`, the application and,
last, the production build of the administration application. The backend serves that build at the
root of its own origin, so a deployment needs no separate web server for the administration
application. To build the image locally, run `be/k8s/scripts/build-image.sh` (it needs `npm ci`
run once in `fe/`).

*The public site's image* is built from `fe/ui-apps/info/Dockerfile`: nginx serving the built
files as user 101 on port 8080, passing only the public, read-only `/rest` paths on to the
backend. Each country builds and publishes its own, from its own build of the site, with
`npm run image:info`; the base product publishes none. In the base product the command is a
manual tool for trying the image locally.

[#the-helm-chart]
=== The Helm chart

The chart in `be/k8s/helm/niord/` deploys one complete stack, one release per country in that
country's own namespace. It has six components, each behind an `enabled` flag:

[cols="20,80",options="header"]
|===
|Component |What

|`proxy`
|nginx, the single public entry point: it sends `/auth` to Keycloak and everything else to the
 backend.

|`app`
|The backend, which also serves the administration application.

|`postgres`
|PostgreSQL with PostGIS.

|`keycloak`
|Keycloak. A cluster can instead use a Keycloak outside the release, shared by several
 deployments.

|`mailhog`
|MailHog, which catches mail on test environments.

|`info`
|The public site, off by default; an environment turns it on with its country's image, under the
 same version as the backend, on a host of its own.
|===

....
browser --> https://<deployment host>  --> proxy (nginx)
                                             |-- /auth/*  --> keycloak
                                             `-- the rest --> app: /rest, the
                                                              administration application

reader  --> https://<public site host> --> info (nginx) -- public /rest paths only --> app
....

Every pod runs as a non-root user and meets the Kubernetes Pod Security level `restricted`. Each
component's service is named `<release>-<component>`, with `-niord` added to the release name when
it does not contain "niord" already: `niord-proxy` in a release named `niord`, `staging-niord-proxy`
in one named `staging`. The chart's version is the application's version, and the image tag defaults to it, so pinning the
chart pins the images. `be/k8s/README.md` describes the values, the two modes of Keycloak
(development, with the test realm, and production), and how to run the whole chart on a local
Kubernetes cluster.

[#deployment]
=== Deployment

The base product deploys nothing itself. Each country takes a new version through a pull request
in its own repository (<<building-a-country>>), builds its images, and deploys them with the
published chart to its staging environment. The configuration of each environment is kept in a
deployment repository of its own, outside this one. Production is to be changed only by a person,
who promotes exactly the version staging has been running; nothing reaches it by itself. A new deployment's database is bootstrapped once
(<<the-bootstrap>>), and its operators then set up its data, as the country kit's operators' guide
describes.
