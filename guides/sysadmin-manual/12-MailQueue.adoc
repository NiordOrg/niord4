[#mail-queue]
== Mail Queue

Niord does not send a mail at once: it puts it in its _mail queue_ and sends it from there. The _Mail Queue_ page
lets a system administrator look through every mail in the queue, sent or not. You open it from *Sysadmin* ->
*Mail Queue*. The page only shows mails: it cannot send, resend or delete one.

image::MailQueuePage.png[Mail Queue, 800]

The picture shows the list filtered on the subject of one mail (see <<mail-filtering,Mail Filtering>>).

Mails in Niord come from a few places:

. An editor mails a selection of messages from the _Messages_ page, as described in the
  link:../editor-manual/manual.html#e-mail-selection-action[E-mail Selection Action] section of the editors'
  manual.
. An editor who writes a comment to a message can mail it to recipients, as described in the
  link:../editor-manual/manual.html#comments-editor-page[Comments Editor Page] section.
. Most mails are sent by mailing lists, as described in the <<mailing-lists,Mailing Lists>> chapter.

Niord deletes a mail from the queue when it is older than the number of days in the setting `mailDeleteAfterDays`
(30 unless it is changed). The page says so above the list ("NB: Mails get deleted after 30 days."). With a value of
0 or less, Niord deletes no mail, and the page shows no such note.

[#sending-mails]
=== Sending Mails

A new mail in the queue is _Pending_. Every minute, Niord sends the pending mails that are due, at most as many as
the setting `mailMaxPerMinute` allows. A mail the mail server accepts becomes _Sent_. When sending fails, Niord
keeps the error with the mail and tries again later: after 1, 5, 15 and then 60 minutes. When the fifth attempt
fails too, the mail becomes _Error_, and Niord does not try again.

So check the queue now and then for mails with the status _Error_, and put right what caused them, such as a
mistyped address of a user or a contact.

A mailing-list trigger that fails also leaves a mail with the status _Error_, which is never sent. Its subject
starts "Not sent: mailing list", and names the list and either the message (a status change trigger) or the trigger
(a scheduled trigger); its last error says why it failed. A scheduled trigger is tried again within the hour, and
leaves at most one such mail a day while it keeps failing.

After a restart, the server builds its text search index again, which takes some minutes on a large database. A
scheduled trigger whose message query has a text term (`query=`) and that runs in those minutes would find only the
messages indexed so far, so in the first half hour after the restart it waits, and is tried again every two
minutes. It leaves one mail with the status _Error_, which is never sent, whose subject starts "Delayed: mailing
list" and names the list and the trigger, and whose last error says that the text search index is being built again
and by when the mail is made, at the latest half an hour after the restart; the server log has one WARN saying the
trigger waits for the index. The trigger's mail is made as soon as the index is complete. When the index is still
not complete half an hour after the restart, the mail is sent all the same, and the log has a WARN naming the
trigger, since the mail may list too few messages.

Niord notes every status change of a message in its database, together with the change, until the mails of the
status change triggers are in the queue. So a status change trigger makes its mails even when the server restarts
just after the change: at once when the server is up again, or within a minute. Niord also notes, for each status
change, which of its triggers are done: their mails are in the queue, or their failure is (the mail with the status
_Error_ above). When a trigger is neither, for example because the database could not be reached for a moment, the
status change is kept and tried again a few minutes later, and only the triggers not yet done are run again: the
mailing lists that got their mail do not get it twice. When the server stops while it is putting a status change's
mails in the queue, that status change is taken again ten minutes later, in the same way. A status change taken
again is mailed for the status it had, so its mail can arrive after the mail of a later status change of the same
message, for example a cancellation. A status change that could not be finished in five attempts (the server
stopped, a trigger hung, or the database could not be reached, each time) is given up: each of its status change
triggers not yet done leaves a mail with the status _Error_, as above, whose subject names its mailing list and whose
last error says it was given up, and the server log has an ERROR naming the message. When even that mail cannot be
saved, Niord tries five more times, minutes apart, and then deletes the status change all the same: an ERROR in the
server log naming the trigger, its mailing list and the message is then the only record of the mail that was due.

The setting `mailValidRecipients` decides who Niord really sends mail to (see <<settings,Settings>>):

* `ALL` sends every mail.
* A comma-separated list of addresses sends mail only to those addresses; the other recipients are left out, and a
  mail with no recipient left fails.
* `LOG`, the value a new deployment starts with, sends no mail at all: Niord only pretends to send it, and the
  queue still shows it as _Sent_. Set the setting to `ALL` when the deployment is to send mail.

Niord reads these settings when the server starts, so a change takes effect at the next restart of the server.

[#mail-filtering]
=== Mail Filtering

The queue may hold thousands of mails, so the list shows 20 mails at a time, with a pager below it. The line above
the list says how many mails match the filter. The _Refresh_ button at the right, two circling arrows, searches
again with the same filter; the list does not refresh by itself.

The fields above the list filter it:

[cols="30,70",options="header"]
|===
| Filter
| Description

| Recipient
| Matches the addresses of the recipients.

| Sender
| Matches the address of the sender.

| Subject
| Matches the subject of the mails.

| All, Pending, Sent, Error
| Shows the mails of one status, or of all of them.

| From date, To date
| The two date fields with a calendar mark, after the status buttons: the first is the _From date_, the second the
  _To date_. They show the mails put in the queue within these dates. Either can be left empty.

|===

The list shows when each mail was put in the queue, its status, its sender, its first recipient (and how many
others it has) and its subject.

[#mail-details]
=== Mail Details

Click the *Open mail details* button (the envelope) at the end of a row to see the whole mail: its sender and
recipients, when it was put in the queue and, by its status, when it is due to be sent (_Due_, for a pending
mail; after a failed attempt, the time of the next one), when it was sent (_Sent_) or when the last attempt was
made (_Last attempt_, for a mail with the status _Error_; a mailing-list trigger's failure record shows no such
row, since it was never tried), the last error and the number of attempts when sending failed, its subject and its
content.
