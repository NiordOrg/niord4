[#settings]
== Settings

_Settings_ are the values that adjust how a deployment of Niord works: its addresses, its languages, how it
sends mail, the map it shows, and much more. Niord keeps them in its database. The _Settings_ page lets a system
administrator see and change them. You open it from *Sysadmin* -> *Settings*.

image::SettingsPage.png[Settings, 800]

Each row shows the setting's key, its description and its value; the value of a password is shown as
"pass:[********]". Type in the _Filter_ field to show only the settings whose key or value contains the text (the
picture shows the settings that contain "map"). The list shows 20 settings at a time, with a pager below it.

[#settings-model]
=== Settings Model

A setting is more than a key and a value. The Niord program _declares_ each setting it reads, and the declaration
gives it these attributes:

[cols="20,80",options="header"]
|===
| Attribute
| Description

| Key
| The unique name of the setting.

| Value
| The value of the setting, in the form its type gives.

| Type
| One of "String", "Password", "Integer", "Long", "Float", "Double", "Date", "Boolean", "Path" and "json".

| Description
| A text saying what the setting does.

| Cached
| Whether Niord may keep the value in memory for a few minutes instead of reading the database each time.

| Web
| Whether the value is passed to the web applications. The administration application reads these values when it
  starts, and a value from the server replaces the value the application was built with.

| Editable
| Whether the setting is shown on this page and can be changed there. The running version of Niord decides this,
  whatever an older row in the database says.

| Scope
| _operator_ for a value a system administrator sets; _state_ for a value only the system writes, which this page
  and the settings import refuse to change.

| Required
| Whether the setting must have a value: Niord refuses to save it empty.

|===

The page lists only the editable settings that the running version of Niord declares. A setting no version
declares any more, such as one of an earlier Niord version, is not listed or exported, and stays in the database
untouched.

The value of a "Password" setting never leaves the server: you can set a new one on this page, but you cannot see
the old one.

[#settings-from-niord-json]
=== Where Settings Come From

When Niord starts, it adds every declared setting the database lacks, with its default value, and it never changes
a value the database already has: a value you set stays until you change it, also when a new version of Niord
has another default. Niord does not add a setting back once its row is gone.

The default value comes from, in this order:

. the file "niord.json" in the server's home folder (the setting `niord.home`), when it has the key;
. the settings file of the country the deployment is built on, or the base product's;
. the default the Niord program declares.

The file "niord.json" gives values only: the type, the description and the flags always come from the program,
whatever the file says, and a key no version of Niord declares is skipped, with a warning in the log. Example:

[source,json]
----
[
  {
    "key"   : "baseUri",
    "value" : "https://niord.example.org"
  },
  {
    "key"   : "authServerUrl",
    "value" : "https://niord.example.org/auth"
  },
  ...
]
----

[#settings-from-environment-variables]
=== Settings from Environment Variables

A system property or an environment variable with the same name as a setting takes precedence over the value in
the database, for as long as it is set. For the home folder, `niord.home`, the environment variable `NIORD_HOME`
works too. For example, start Niord with `-Dniord.home=/srv/niord`, or with the environment variable
`NIORD_HOME=/srv/niord`.

Niord does not start when the home folder names no folder: its value is empty, or names an environment variable
that is not set, as `${NIORD_HOME}` does without `NIORD_HOME`. The log then says `niord.home cannot be resolved`,
with the value, where it came from and how to set it.

The _Settings_ page still shows and saves the value in the database, but while such a system property or
environment variable is set, Niord uses that instead.

[#settings-from-code]
=== Settings from Code

The Niord program declares its settings in its code, with their type and default value. For example:

[source,java]
----
@Setting(value = "mailDeleteAfterDays", defaultValue = "30", type = Type.Integer,
         description = "Delete scheduled mails older than the given value. "
                     + "A non-positive value means never.")
volatile Integer mailDeleteAfterDays;
----

A setting you save on this page takes effect at once, without a restart: the next mail, map picture, search or
batch job uses the new value. Where several servers run one deployment, the others follow within about half a
minute. A system property or an environment variable of the same name still wins over the saved value (see
<<settings-from-environment-variables,Settings from Environment Variables>>).

A setting changed outside this page, by SQL or by restoring the database under a running server, is not taken at
once: the servers take it at their next start, or within about half a minute after the row `settingsChangeCount` is
raised by one, which makes every server read its settings again:

[source,sql]
----
UPDATE "Setting" SET setting_value = (setting_value::bigint + 1)::text
 WHERE setting_key = 'settingsChangeCount';
----

The row is there once a setting has been saved on this page. The settings that are not on this page (below) and
`messageIndexDeleteOnStartup` are taken only at the next start.

A few settings are worth knowing about before you change them:

* `messageIndexDeleteOnStartup` acts only when the server starts, so a change to it applies at the next start. Its
  description says so: "Applies at the next start."
* `messageIndexIncludeDeletedMessages` decides whether the text search index holds deleted messages. A change builds
  the search indexes again, which takes some minutes on a large database. Meanwhile the message list shows its
  warning that the index is still being built, as it does after a restart, and `GET /rest/monitor/message-index`
  answers `"complete":false`. A scheduled mailing-list trigger with a text term waits for the index then, as it
  does after a restart (see <<mail-queue,Mail Queue>>).
* `wmsProvider`, `wmsLayers` and `wmsPassword` (the provider's token) choose the sea chart. The server fetches the
  next tile with the new value, and its own tile cache needs no emptying. A browser, however, keeps a tile it has
  shown for up to a day, so a place a user has already looked at can show the old chart for up to a day, or until
  the browser's cache is emptied. When you change both the provider and its token, the new provider is asked with
  the old token between the two saves, and its tiles may fail for that moment.
* `mapImageSize` is the size of the map pictures of messages. After a change, each picture is drawn again at the
  new size the first time it is asked for.

These settings are not on this page, because a change under a running server would do harm (a batch job would be
split across two folders, or the search would answer from another folder's index): `authServerUrl` (the address of
Keycloak), `batchJobRootPath`, `messageIndexPath` and `publicationPreviewRootPath` (the folders of the batch jobs, the
text search index and the publication previews) and `vipsPath` (a program on the server that draws thumbnails
faster). The deployment sets them, with a system property or an environment variable of the same name, or, for a
new database, in "niord.json" (see <<settings-from-niord-json,Where Settings Come From>>). The server uses the
value it had when it started, and the settings import skips them.

A database restored from another system brings that system's rows for these five settings, and this page cannot
correct them. To give one of them another value, set a system property or an environment variable of the same
name: it wins over the row, also when it is empty. An empty `vipsPath` (for example `-DvipsPath=` among the
server's Java options) switches the program off, and the server draws the thumbnails itself. For the three folders
and `authServerUrl` an empty value is no way to clear the row: an empty folder is the server's working folder, and
with an empty `authServerUrl` the server's calls to Keycloak fail with "No authServerUrl setting defined". To go
back to the default instead, delete the row: from the next start the value of "niord.json", else the default in the
code, applies. A change of one of these rows by SQL is taken at the next start.

[#settings-an-operator-sets]
=== Settings to Set for a New Deployment

Among the many settings, these are the ones a system administrator usually sets first:

[cols="35,65",options="header"]
|===
| Setting
| Description

| `baseUri`
| The address of the Niord server.

| `adminAppUrl`
| The address of the administration application. Links to messages in mails point here. When it is empty, the links
  use `baseUri`.

| `authServerUrl`
| The address of Keycloak (see <<keycloak-integration,Keycloak Integration>>). The deployment sets it, not this page
  (see <<settings-from-code,Settings from Code>>).

| `country` and `organisation`
| The country and the organisation that run the deployment. Both are required.

| `documentationUrl`
| The address of the user guides. Every help button of the administration application opens a page under this
  address; the default is `https://docs.niord.org`.

| `mailSender`, `mailValidRecipients`, `mailDeleteAfterDays`
| The sender of Niord's mails, who receives them, and how long the mail queue keeps them (see
  <<mail-queue,Mail Queue>>). A mail that `mailValidRecipients` keeps from its recipients reads _Held_ in the mail
  queue: every mail while it is `LOG`, when no mail leaves the server, and, while it is a list of addresses, every
  mail with a recipient who is not on the list, whose copy goes to the list's first address instead; on a deployment
  whose setting is a list, most mails show as _Held_. A system administrator can send a held mail again once the
  setting is changed (see <<send-again,Sending a Mail Again>>).

| `adminIntegrationPageEnabled`
| Shows the _Niord Integration_ page in the *Sysadmin* menu (see <<integration,Integration>>).

| `batchFileExpiryDays`
| How many days the files of batch jobs are kept (see <<batch-jobs,Batch Jobs>>).

|===

[#editing-a-system-setting]
=== Editing a System Setting

Click the *Edit Setting* button (the pencil) of a row. The editor opens beside the list:

image::SettingEditPage.png[Setting Editor Page, 325]

You can change only the value. The field depends on the type of the setting:

* a checkbox for "Boolean";
* a number field for "Integer" and "Long", and one that takes decimals for "Float" and "Double";
* a hidden field for "Password";
* a code editor for "json", where *Save Setting* is disabled while the text is not valid JSON ("Invalid JSON — fix
  the syntax to save.");
* a text field for the other types.

Niord checks the value when you save: a value that does not fit the setting's type, an empty value for a
required setting, or a value outside what the setting allows, is refused ("Error saving setting"), and the setting
keeps its value. Since a saved value acts at once, a few settings are held to a range: `batchFileExpiryDays` and
`firingExerciseScheduleDays` are at least 1, and `mapImageSize` and `mapImageZoomLevel` must give a map picture
Niord can draw.

[#importing-and-exporting-settings]
=== Importing and Exporting Settings

The menu of the gear button (_Settings actions_) has *Export...* and *Import...*.

The file is a JSON list of settings, for example:

[source,json]
----
[
  {
    "description": "The base application server URI",
    "key": "baseUri",
    "type": "String",
    "value": "https://niord.example.org"
  },
  {
    "description": "The sender e-mail address.",
    "key": "mailSender",
    "type": "String",
    "value": "niord@niord.example.org"
  },
  ...
]
----

The import runs as the _settings-import_ batch job, which you follow on the <<batch-jobs,Batch Jobs>> page. It only
changes the values of settings this deployment has. It skips, each with a line in the job's log, a key the running
version of Niord does not declare, a _state_ setting, a setting the deployment sets (see
<<settings-from-code,Settings from Code>>), a key the database has no row for, a value that does not fit the
setting's type, and a required setting that the file gives no value. The values it changes take effect at once,
as a save on this page does.
