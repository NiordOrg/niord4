# Country deployments

Niord is deployed once per country. Each deployment is a **separate build artefact** with its own
brand, language list and channel plugins baked in, built from the country's own repository on the
published source zip of the base product. There is no runtime country switch, no country query
parameter, and no country code in the app state.

The base product is country-unaware: no country, English only, no authority footer. Every place a
country may differ is a seam with a neutral default here, and a country's differences are files in
its own repository, set up against the zip with the kit in `country-kit/`: a manifest
(`niord-country.json`) naming its languages, files at the seams' conventional paths, its own
branding and brand tokens, and `node setup.mjs` generating the workspace. The guides in
[country-kit/docs/](../../country-kit/docs/README.md) say who does what, and the
[country guide](../../country-kit/docs/country-guide.md) gives the standard path of adding a
country, and the [in-depth guide](../../country-kit/docs/country-guide-in-depth.md) the reference;
[country-kit/README.md](../../country-kit/README.md) is the reference they link into, and
[fe-country-split-plan.md](../../docs/fe-country-split-plan.md) §5 the record of the steps. The
example country `xx` in `country-kit/example/` is a complete one, set up and built from
outside the tree by `verify-local` and Frontend CI.

This document describes the administration app's side of the base product. The public site
(`ui-apps/info/`) has the same three kinds of seam with files of its own — a `default/` folder
holding `info.config.ts` and `language.config.ts`, the same brand token files, and an asset overlay
that carries its branding and legal documents — in two standalone configurations, `production` and
`local`. Its `default/` folder also holds `country.routes.ts` (the country's own pages, the layout's
last child) and `country.providers.ts` (its slots; one exists, `layout.beforeFooter`), both empty in
the base product; its [AGENTS.md](../ui-apps/info/AGENTS.md) says how they fit together.

> Language switching is **not** country switching. A user flips the UI language at runtime through
> Transloco; that never changes which artefact is running. See [Languages](#languages).

## The seams and their defaults

Each seam is a base product file with a neutral default. A country's set-up replaces the default
with the country's file when its repository has one at the seam's path (relative to the country's
`fe/`; [country-kit/README.md](../../country-kit/README.md) → _The seams_):

| What                       | Mechanism               | Base default                                               | A country's file                                           |
| -------------------------- | ----------------------- | ---------------------------------------------------------- | ---------------------------------------------------------- |
| Hooks and slots            | `fileReplacements` (TS) | `country-specific/default/country.providers.ts`            | `admin/app/country.providers.ts`                           |
| Own pages and menu entries | `fileReplacements` (TS) | `country-specific/default/country.{routes,menu}.ts` (none) | `admin/app/country.routes.ts`, `admin/app/country.menu.ts` |
| Language list + order      | generated (TS)          | `country-specific/default/language.config.ts` (English)    | generated from the manifest                                |
| Brand tokens               | `styles[]` array (CSS)  | `styles/tokens.active.css` (imports `tokens.default.css`)  | `styles/tokens.<cc>.css`                                   |
| Branding, legal texts      | `assets` overlay        | — (no footer)                                              | `admin/assets/branding/`, `admin/assets/legal/`            |
| Environments (dev, test)   | `fileReplacements` (TS) | `src/environments/` (neutral)                              | `admin/environments/environment.<configuration>.ts`        |

The UI JSON bundles and the flags come from the language packs, staged into `.niord/build/<app>/`
and read through one staged input whose ignore list picks the ones the configuration's
`language.config.ts` names, and all shared features serve every build; `npm run contents:check` fails
a configuration that ships a bundle, flag or overlay file it does not name, or writes one output from
two sources. No flag lives in an overlay.

Every base configuration is standalone, since Angular merges composed configurations shallowly — a
later configuration's `fileReplacements` replaces an earlier one's rather than adding to it — and a
country's configurations are generated by the kit, each standalone as well.

### Why the CSS swap is different

The brand stylesheet is chosen by the `styles[]` array rather than through `fileReplacements`, which
accepts only JS/TS/JSON — see [`styling-reference.md`](styling-reference.md) for the mechanics and the
cascade-order rationale.

## The token contract

Brand styling is expressed only as CSS custom properties. Component code, the Tailwind `@theme`
bridge and the `@layer components` classes all read tokens through `var(...)`, so a country overlay
never touches a component.

The tokens split in two: `styles/tokens.base.css` is country-locked and loaded in every build, while
`tokens.default.css` and a country's `tokens.<cc>.css` carry the brand values, one of them per build.
A country's brand file is a copy of the default with different values and **nothing else**. Both
catalogues — which token is in which file, and what each one does — live in
[`styling-reference.md`](styling-reference.md).

Locking is a **convention, not a mechanism**: the brand file is loaded after the base file, so a
redeclared `:root` variable would win. Redeclaring a base token in a country's brand file is a review
failure, not a build failure.

Rules that are easy to get wrong:

- **The accent scale is not the action colour.** The default file aliases
  `--niord-action-primary-bg` to _primary_ and reserves the accent for state and wayfinding —
  selection wash, the header brand bar, badges. The alias is the country-flippable indirection, so a
  country that wants accent buttons flips the alias rather than restyling `.btn-primary`.
- **The destructive red is semantic, not brand.** `--niord-action-danger-bg: #b52d20` is declared in
  the default file and kept by a country's copy. It sits there for reach, not because it is a
  branding axis — changing it needs a deliberate reason.
- **The 18 status tokens are independent.** The default file happens to give Draft and Verified the
  same values, and Cancelled and Expired the same values. Do not collapse them into aliases; a
  country that needs to distinguish them must be able to, without touching component code.
- **Radius is a real axis.** The default uses 5/8/12 px; one country uses 3/4/6 px for a flatter,
  more official feel. A country tunes the tone of the whole UI here.
- **`--niord-font-size-adjust` keeps a non-system font at parity.** One country ships Verdana, whose
  x-height is much larger than `system-ui`; `font-size-adjust: 0.49` on `html` normalises the
  rendered size so no component needs a per-brand font-size. The default sets `none`. A country
  adopting its own face sets this instead of re-tuning type scales.
- **Contrast floors are part of the contract.** `--niord-fg-subtle` is used for placeholders and
  captions at body size, so it must stay at or above 4.5:1 on `--niord-surface`. The default file
  holds a value just above the floor and documents the measurement inline; a country's file must do
  the same. Two more tokens carry a floor of their own: each status `-fg` is text on its own `-bg`,
  so it holds 4.5:1 on the solid tint and on the status badge's 65 % wash of it, and
  `--niord-surface-500` draws the border of every form field, so it holds 3:1 on `--niord-bg` and on
  `--niord-surface`.
- **Title colour carries hierarchy on hue.** `--niord-fg-title` points at the brand primary because
  body text is near-black in the default file and in a country's. This matters more for a face
  without a 500 weight (Verdana, say), where `font-medium` renders identically to normal text and
  hue is the only axis left.

## The behaviour seam

Behavioural country differences go through **multi-provider DI tokens**, never through a branch.

`ui-apps/admin/src/app/country-specific/default/country.providers.ts`, and a country's
`admin/app/country.providers.ts` in its place, exports exactly one function:

```ts
provideCountry(): EnvironmentProviders
```

`app.config.ts` calls it once, at the root injector, after the core promulgation registrations, so
its multi providers add to the core's. The `default` implementation returns
`makeEnvironmentProviders([])`, so the seam costs nothing when a country adds nothing. A country
provides two kinds of thing there:

- **Hooks** — the base product's tokens a country adds its own implementations to. Two exist:
  `PROMULGATION_RENDERERS` and `PROMULGATION_EDITORS`, one `{ serviceId, component }` per channel.
- **Slots** — named places in base product templates (`<app-slot name="…" />`) where a country
  shows a component of its own: `provideSlot('home.welcome', () => import('./…').then((m) => m.X))`.
  The loader is a dynamic import, so the component lands in a lazy chunk; a slot takes no inputs, and
  with nothing registered it renders nothing. One slot exists in this application, `home.welcome`,
  at the end of the front page's welcome panel (`shared/slots/component-slots.ts`).

Each hook and slot is a promise the base product keeps across versions, so one is added only where a
country needs it, deliberately, with a neutral default and a spec; `country-kit/seams.json` names
every one.

Two more files of `country-specific/default/` are seams with nothing in them, which a country
replaces with its own `admin/app/country.routes.ts` and `admin/app/country.menu.ts`:

- `country.routes.ts` — the country's own pages, the default export `Routes`, which `app.routes.ts`
  loads lazily after every base route. Every top-level entry declares `canMatch: [roleGuard]` with a
  non-empty `data.rolesRequired`, or `data: { public: true }`, or is a redirect;
  `core/country/country-routes.ts` leaves out and logs any other, so a forgotten guard closes the
  page rather than opening it.
- `country.menu.ts` — `COUNTRY_MENU_ENTRIES`, each `{ after, labelKey, icon, routerLink, roles }`: the
  base item it follows (`messages`, `editor`, `schedule`, `admin`, `sysadmin`; it keeps that place
  when the item is hidden), a `country.*` label key, a registered icon, its page, and the roles that
  see it (`[]` for everyone, anonymous included). The main menu applies the same role check as to its
  own items.

`country.providers.spec.ts` asserts that the default exports exactly `provideCountry`, that it
registers no promulgation renderer or editor (audio is the base product's own), and that the default
routes and menu are empty. A country's files are checked by its set-up against `seams.json`, so one
that renames or drops the function fails there, before anything is built.

Both registries are dispatched by `promulgation.type.serviceId`, and a `serviceId` with no
registered plugin renders nothing — which is how a build tolerates data carrying a channel it has
no plugin for. The registry rules themselves (root-injector registration only, dispatch by id, an
unregistered id is a first-class case) are owned by [`architecture.md`](architecture.md) →
_Promulgation registries_.

### Worked example — the example country's harbour bulletin

The example country (`country-kit/example/`) has a promulgation service of its own, the harbour
bulletin `xx-bulletin`. The whole of it in the administration app is:

```
country-kit/example/fe/admin/app/
  country.providers.ts               provideCountry(): { serviceId: 'xx-bulletin', component } into both tokens
  bulletin/bulletin-view.ts          read-side renderer + its typed model
  bulletin/bulletin-edit.ts          editor-side form
```

The audio channel is the base product's own, registered beside NAVTEX, Twitter and SafetyNET. An
editor component stays free of the editor facade because `NgComponentOutlet` binds inputs only, so
every callback it needs arrives as one `context` input (`patch`, `generate`, `reformat`, `busy`,
and the reactive `messageStatus`). A country channel therefore depends on the context interface,
not on feature internals.

Country code imports the base product only through the country API, `@niord/admin/api`, and
otherwise stays inside its own folders; the country lint fails anything else. See
[`architecture.md`](architecture.md) → _The country API_.

### The prohibition

> Never write `if (country === 'dk')`, a country code constant, or any equivalent runtime branch.

There is no country identifier in the running app to branch on, and adding one would convert a
build-time fact into runtime state that every feature would then have to reason about. If a
difference cannot be expressed as a token, a language-list entry, a DI registration or a
configuration value, the correct move is to add a new extension point — a token with a neutral
default — not a branch.

### Choosing where a difference lives

Classify in this order and stop at the first that works:

1. **Branding** — a token value, or the country's branding overlay: a text that names the authority,
   a logo, a legal document.
2. **Configuration** — an `AppConfig` field (build default; most fields are overridable at runtime
   by the backend web settings, see [`platform.md`](platform.md)).
3. **Content** — a translation key, overridable at runtime through the sysadmin Dictionary. A key
   the base bundles carry never names an authority.
4. **Behaviour** — a multi-provider DI registration with a neutral default.
5. **Country code** — a file in the country's repository at a seam's path
   ([country-kit/README.md](../../country-kit/README.md)).

Assume a country difference is not a code difference until proven otherwise.

## Languages

The backend settings are authoritative: `siteLanguages` controls the UI language menu,
`modelLanguages` controls message and localized-data editors and output, and `defaultLanguage`
controls missing-text fallback independently of either list's order. Deployment configuration seeds
missing settings; existing database values survive restarts. The frontend loads the settings API
before translations and domains, and uses its build's language configuration when settings are
absent or the API is unavailable. Refresh after changing language settings.

`infoSiteLanguages` and `infoDefaultLanguage` are the public site's equivalents of the two lists
above: `fe/ui-apps/info/` reads them, this application never does, so the two sites can offer different
languages from one backend.

The build's `language.config.ts` exports `COUNTRY_LANGUAGES`: language metadata
(`availableLanguages`: label, code, locale and, where the build ships one, a flag), the UI bundles
the build ships (`uiLanguages`, `en` only when named: every bundle is staged complete, its missing
keys filled from `en`, so there is no runtime fallback language and a key still missing renders as
the key), the languages with a branding file (`brandingLanguages`), the default language, and
optional `siteLanguages` / `modelLanguages` fallback lists. A configuration without separate lists
uses `availableLanguages` for both. The base product's, `country-specific/default/language.config.ts`,
is English only; a country's is generated from its manifest by the kit's set-up.

Each list determines its own display order. The UI list is restricted to the bundles named in
`uiLanguages`; unsupported UI codes are diagnosed and omitted. Model-only languages need no JSON UI
bundle: they use the default UI bundle plus existing dictionary entries. A language with no flag in
the configuration — the Danish content of a deployment running the base build, say — renders as
its code in text wherever a flag would stand, never as a guessed image path.
The dictionary structure and key ownership remain unchanged.

Missing dictionary/display text uses the requested language, configured default, then another
stored translation. Editors show actual values and never persist fallback text as a translation.
Source, area and category names require the configured default language; other translations are
optional. Publications retain their series-specific requirements. Print and send-mail offer a
model-language selector. Message search searches all model languages while keeping the current UI
language for display. Relevance results are grouped by language: the UI language comes first,
then the remaining model languages in application order. Each group retains its index score order;
duplicate messages keep their first position. This is not a global score ranking across languages,
and performs one index query per model language.

Admin lists for parameter types, sources, areas, template categories and publication categories
offer a **Model language** picker, as do list-value and template-parameter tables inside editors.
The picker uses `modelLanguages`, so a model-only language remains readable without switching the
UI. Selection belongs to the current page and is shared with its nested parameter tables; a new
page initially uses the UI language when supported, otherwise the default model language.
An explicit choice survives UI language changes while that page remains open. Missing text uses
the same default-language fallback. Switching the displayed language neither changes record data
nor marks an editor as changed. Displayed model fields carry their actual text language for
assistive technology, including when the text comes from a fallback language. Plain identifiers
and excluded text remain unlocalized.

FreeMarker resources retain their existing structure: localized files get language siblings and
inline language branches/macros gain equivalent branches/arguments. Missing localized files first
allow FreeMarker to resolve the unsuffixed base file; when it is also absent, the default-language
sibling is used. Fixed-language promulgation channels and excluded data models retain
their existing behaviour.

### A language is a pack

`languages/` here holds the base product's one pack, `en` (its flag drawn as plain SVG and rendered
to PNG by the command `languages/en/ATTRIBUTION.txt` records). Every other language is a pack in a
country repository — the country's own, or one it pins from the language's home — held to `en` by
that country's pack check; a pack's layout, its status lists, publishing and pinning are in
[country-kit/README.md](../../country-kit/README.md) → _Language packs_.

### Per-country text

There is **no** per-country translation bundle. The `en` pack's
`languages/en/i18n/admin/en.json` is this application's bundle here, staged into each build by
`npm run languages:stage` (every start and build script runs it first); a country's packs are staged
the same way in its workspace. A country's own words — the footer's authority link and copyright,
its logo, the legal documents' titles — are its branding file, `admin/assets/branding/<lang>.json`
in its repository, which the loader merges over the one bundle it fetches (bundle ← branding ←
Dictionary, [`platform.md`](platform.md)); the disclaimer and the cookie statement are
`admin/assets/legal/<doc>.<lang>.html`, rendered by one legal-document dialog. The footer shows only
what the branding sets, so the base build has none. Wording that differs per deployment is handled
at runtime: `core/i18n/dictionary-overrides.service.ts` fetches the backend `web` and `message`
dictionaries (anonymous endpoints, so they resolve pre-login) and merges them over the bundle and
the branding by key; the branding keys keep the names they had as bundle keys, so a deployment's
existing Dictionary rows still apply. An override that would drop an interpolation placeholder the
base value carries is refused, so an administrator can re-word any label but cannot break its data.

Choose the bundle for wording that belongs to the product, the branding file for wording that names
the authority, and the Dictionary for wording a deployment's administrators own.

## Adding a country or a language

A country is added in its own repository, with nothing changed here. The
[country guide](../../country-kit/docs/country-guide.md) gives the standard path (the release and
init's answers, set-up and the local run, then make it yours and deploy), whose Quick start is the
recipe to [add a country](../../country-kit/docs/country-guide.md#quick-start), and the in-depth
guide the recipe to [add a language](../../country-kit/docs/country-guide-in-depth.md#recipe-add-a-language); the
[designers' brief](../../country-kit/docs/designers-brief.md) covers the theme.
[country-kit/README.md](../../country-kit/README.md) says how each is done —
[Starting a country](../../country-kit/README.md#starting-a-country--init) for the first set-up,
[Language packs](../../country-kit/README.md#language-packs) for a language. A new language is a pack
in a country repository, never a folder under `languages/` here.

## Branding work list

These items are also tracked in the repo-wide [`backlog.md`](backlog.md); they are restated here
because together they are the brief for a country-branding task. They are hard-coded or shared
today. None of them is a bug in the running product; each is a point where a second brand would
currently leak through.

**Shell and boot**

- `ui-apps/admin/src/index.html` hard-codes `<title>Niord</title>`, `lang="en"` and the splash palette
  (`#f8fafc`, `#475569`, `#cbd5e1`, `#1e3a5f`) as literals. The splash is deliberately
  self-contained — it must paint before any app CSS loads — so it cannot consume tokens; a branding
  task has to parameterise it at build time or accept one neutral splash for all countries. The
  `lang` attribute is corrected at runtime by `LanguageService`, so it only affects the splash
  phase. `appName` from `AppConfig` drives the _router_ tab title, not this tag.
- `ui-apps/admin/public/favicon.ico` is a single shared file, the base product's and not brandable;
  nothing in a base configuration replaces it.
- The header logo (`assets/img/niord_white.png`) and the home-page logo (`assets/img/niord.png`)
  are the Niord mark, fixed by the base product and never brandable; no country overlay carries a
  copy.
- The product name and its NIORD acronym rendering on the home page are intentionally untranslated
  and un-keyed — the product name is identical in every deployment. Do not "fix" this into a
  translation key.

**Assets**

- A country's overlay (in its repository) carries its branding and legal documents; `index` is
  still shared, so the page title and splash are the same in every artefact.
- The `en` pack's flag is here, drawn for Niord from the SVG beside it, and a country's packs carry
  theirs; a language with no flag renders as its code. The footer logo is branding and exists only
  where a country names it.
- Footer legal text — the copyright line, its link, the logo and the disclaimer and cookie dialogs —
  is the country's branding file and legal documents; a deployment still retunes the branding keys
  through the sysadmin Dictionary with no rebuild, and the documents by a rebuild of its overlay.

**Configuration and behaviour**

- `PROMULGATION_ADMIN_PLUGINS` (the sysadmin promulgation-type drawer's per-service configuration
  sections) has a **core** provider only, so a country service has a renderer and an editor but no
  admin section (the base product's Audio has none either). An admin section for a base service such
  as Audio would be a core `PROMULGATION_ADMIN_PLUGINS` registration; one for a country's own
  service needs a new seam — a hook in `country-kit/seams.json` and the country API.
- The behavioural country seams are the ones `country-kit/seams.json` lists: `country.providers.ts` with the
  hooks (`PROMULGATION_RENDERERS`, `PROMULGATION_EDITORS`) and the component slots (`home.welcome`),
  `country.routes.ts` and `country.menu.ts` for a country's own pages, and the environments. Anything else a
  country needs will require a new hook or slot with a neutral default.

**Tokens**

- `--niord-primary-soft` is declared in `tokens.default.css`, and so in every country's copy, and
  consumed nowhere. Either give it a use or drop it from the contract.
- Dark mode is pre-wired and empty: the shared `styles/theme.css` binds Tailwind's `dark:` variant to
  an `.app-dark` class on the root element, for both applications, but no `tokens.dark.css` exists and nothing toggles the class. Adding
  dark mode is authoring a scoped token file and a toggle — deliberately not a per-component
  rewrite. It multiplies with countries, so decide whether dark is per-brand before starting.
