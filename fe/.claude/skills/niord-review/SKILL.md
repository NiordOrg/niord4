# Niord review

Review a change set against the rules this repository has written down. Every finding cites the
document that owns the rule; the skill adds no rules of its own. Findings are actionable: severity,
where, what is wrong, which rule, the fix.

## Inputs

- **Scope** — one of: the current branch against `main` (default: `git diff main...HEAD`), an
  explicit file or folder list, or a pull request (`gh pr diff <n>`). Ask when unclear.
- **Depth** — a full pass reads every changed file plus the callers of any changed public symbol;
  a quick pass reads the diff only. Default to full for anything touching `core/`, `shared/` or a
  facade.
- **Application** — which of the two the change reaches: `ui-apps/admin/` (the administration
  app), `ui-apps/info/` (the public site), or both, which is what a change to `styles/`,
  `shared-map/`, `shared-html/` or the workspace configuration reaches. Read it off the diff.

Before reading the diff, read the checklist in [docs/definition-of-done.md](../../../docs/definition-of-done.md)
and the sections of the owning documents the change touches (a map change → `docs/architecture.md`
→ _The map layer_ and `docs/map-portrayal.md`; a form → `docs/angular-conventions.md` → _Signal
Forms_; publications → `docs/publications/domain-rules.md`). The checklist is written for the
administration app. For a change to the public site, also read
[ui-apps/info/AGENTS.md](../../../ui-apps/info/AGENTS.md), which is the rule wherever the two
differ: the public site has no edit flow and bans Signal Forms, adds no visible text but required
accessibility labels, and takes its time zone from the country — so a missing form there is not a
finding.

## Rules of the review

- Report only what the change introduced or touched. A pre-existing defect on an unchanged line is a
  separate note under the verdict, not a finding against the change.
- One finding per defect, anchored at the line that has to change — not at every line that shows
  the symptom.
- Verify before reporting: open the file, follow the caller, run the guard. A finding you could not
  verify is marked _unverified_ or dropped.
- Never restate a `docs/` rule inside a finding; cite it. Where two documents disagree, that is a
  finding against the documents, filed under _Comments and docs_.
- A deliberate limit listed in `docs/backlog.md` → _Deliberately not built_ is not a finding.

## Output

1. **Findings**, most severe first. One per line block:
   `severity` (`high` = ships a defect or breaks a non-negotiable, `medium` = convention, `low` = nit)
   · `path:line` · what is wrong · the owning document and section · the fix.
2. **Definition of Done**: each gate from the `docs/definition-of-done.md` section of every
   application the change reaches as _pass_ / _fail_ / _not applicable — reason_, with the command
   or file that proves it.
3. **Verdict**: _ready_, _ready after the listed fixes_, or _not ready_, in one sentence.

A rule you could not find in `docs/` is not a finding; say so and suggest where it should be
written.
