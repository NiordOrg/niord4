# The screenshot data: niord_guides and ~/.niord-ng-guides

The user-guide screenshots are taken on a copy of the local Danish test data with the personal data removed.
These scripts make that copy, the same way every time.

**The rule: `niord_test` and `~/.niord-ng-dk` are never modified.** They are only read: `niord_test` by `pg_dump`
inside the `niord-db` container (as the launcher's `--own-db` copies a database), `~/.niord-ng-dk` by `robocopy`.
Everything is written to `niord_guides` and `~/.niord-ng-guides`, which are deleted and made again on every run.

The scripts live in `fe/guides-shots/data/`, beside the screenshot rig that photographs the copy (its README is
one folder up); each finds its own files by its own path, so it runs from any folder.

## Re-run

From Git Bash, or from PowerShell through Git's bash, at the repository root:

```
bash fe/guides-shots/data/make-guides-db.sh     # ~7.5 to 11 min: niord_guides (the history snapshots ~1.5 min of it)
bash fe/guides-shots/data/make-guides-home.sh   # ~13 min: ~/.niord-ng-guides (1 GB of repository files, read twice for addresses)

& "$env:LOCALAPPDATA\Programs\Git\bin\bash.exe" fe/guides-shots/data/make-guides-db.sh
```

To change only what `prepare.sql` sets, on a copy that already exists (it is idempotent, but for the batch job records:
it deletes every `BatchData` row, the rig's own runs' too, so apply it while no job runs), apply that one file:

```
docker exec -i niord-db psql -X -U niord -d niord_guides --single-transaction -At -f - < fe/guides-shots/data/prepare.sql
```

`english.sql` is applied the same way, after `prepare.sql` (it is idempotent too, and prints one line per group of
rows with the number it changed, 0 on a second run), and `node fe/guides-shots/data/english-history.mjs` after it.
Piped through PowerShell its æ, ø and å are garbled: from PowerShell, copy it into the container (`docker cp`) and run
`psql -f` there.

The backend keeps settings in a cache, so a setting changed in the database takes effect at its next start; to change
one while it runs, also save the same value on the sysadmin Settings page (or `PUT /rest/settings/setting/<key>` as
sysadmin). The same holds for the dictionaries, the promulgation types and the script resources `english.sql` changes, which
the backend reads once at its start or keeps in its entity cache: after applying it to a copy a backend runs on, start the rig again (`start-rig.sh`).

Needs: the shared containers running (`niord-db`), Docker on the PATH, node (for the dictionary count and for
`niord.json`), robocopy (Windows). Stop a backend running on `niord_guides` or `~/.niord-ng-guides` first: the
database is dropped with `--force`, which ends its sessions. After the run, start the rig and run the repository
import once ("After a backend start", below).

## What the scrub does, in short

- **Users**: every row gets an invented name from a fixed list keyed by its id, a login `first.last` and the
  address `first.last@example.org`. Roles are not in the database: they come from the Keycloak token, and a login
  finds its row by `preferred_username`. The four local logins of `be/keycloak/niord-realm-local.json` (sysadmin,
  admin, editor, user) get rows that mirror the realm (`Local Sysadmin`, `sysadmin@example.org`, ...), so their first
  login changes nothing; the row for `user` is inserted, the other three exist in `niord_test`.
- **Comments**: the text becomes a neutral sentence from a fixed list; author, message, dates and acknowledgement stay.
  The addresses a comment was mailed to become invented people on example.org.
- **Mailing lists**: 40 invented contacts on example.org and two invented users per list (13 to 18 recipients a list);
  `niord_test` had none.
- **Saved filters and tags** named after a colleague (`Korrektur <name>`) get an invented first name; a colleague's
  initials in a tag or filter (`Afventer godkendelse fra <initials>`) become `fra redaktøren`, or invented initials.
  The initials are the 2-5 letter local parts of the comment addresses and the 2-5 letter logins, upper case, matched
  with letter boundaries (so `TEST_<initials>` counts); functional logins and mailboxes (ako, vagts, vrag) are left out.
- **Test messages named after a colleague**: a never-public message (no publish date) whose title or subject is only
  staff names or initials, "test", "diverse" and the country name is deleted with every dependent row and its history
  (gzip snapshots cannot be rewritten in SQL). In `niord_test`: 2 messages, 20 history rows; with them goes one NM
  draft listed by id whose title and subject are three first names and nothing else. Real drafts that only
  contain a name ("Kong Christian X's Bro") stay.
- **A private contact in a published notice** (listed by short id in `g_private_contact`: GL-027-22, a lost research
  buoy, "if found contact <a named person>, tlf <number>"): the contact becomes Arktisk Kommando / Joint Arctic
  Command, the notice's 5 history rows are deleted and the words leave its search row.
- **A private person in a source or a notice**: `<company> v/<name> <date>` (v/ is c/o) in six notices' sources keeps
  the company and the date; a private mailbox in two notices (`g_private_mail`, by short id) becomes an invented one on
  example.org; the messages' history snapshots are deleted.
- **A person's address in any text** (since 2026-11-14): the users' addresses and the addresses comments were mailed
  to, but not the functional mailboxes (the logins and mailboxes the staff words leave out), and the private mailbox
  above, are read from the copy before the scrub rewrites them. Wherever a text column of any table gives one
  (message titles, parts, sources, references, promulgations, attachments, publications, templates, settings, ...)
  or a search row, it becomes the invented address the person has in `User` (or in `Comment_emailAddresses`):
  case-insensitively, inside `mailto:` links too, wherever the whole address stands. The history snapshots are gzip,
  so `english-history.mjs` replaces the same addresses there, finding each person's invented address in
  `guides.scrub_mail`, which holds the invented addresses by the source row and no real one. `check-names.sh` fails
  the run when an address of `niord_test`'s persons is still in any text, JSON or search column,
  `english-history.mjs` when one is still in a snapshot. Left as they are: a duty mailbox in message parts and NAVTEX
  texts (one of the functional mailboxes; the audio texts with it are blanked by `english.sql`, so the copy has
  none), and unit mailboxes at the staff's domains (written as abbreviations; no rule tells a former colleague's
  initials from them).
- **An address of a person's form** (since 2026-11-14): an address whose local part is a word, a single letter and a
  word (first name, middle initial, last name; the form is `guides.scrub_shape`, written once in `scrub.sql`) and
  that belongs to no person above is a person's too. Each such address becomes one invented address,
  `duty.officer<N>@example.org`, the same way and in the same places as a person's address (the rank N in
  `guides.scrub_mail`); `check.sql` fails the run when one outside example.org is left in a text, JSON or search
  column (also with the at-sign as an entity or URL-encoded), `english-history.mjs` when one is left in a snapshot.
  The measurement behind the form (on `niord_test`, the texts the scrub keeps, the search rows and the snapshots): no
  role mailbox has this form, and the addresses of the form `word.word` stand in comment texts only, which the scrub
  replaces.
- **Default-deny for addresses** (since 2026-11-14, the third round, under the owner's "remove GDPR information"): no
  rule can tell a mailbox that is a first name or initials from a role by its form, so an address outside example.org
  is kept only when it is known to be a role: its local part is on the functional list (`g_functional_login`), or
  every word of its local part (split at dots, hyphens, underscores and digits) is on `scrub-lists.mjs`'s list of
  generic role, department and unit words and plain codes (`ROLE_WORDS`, built from the data; no person's name, no
  whole address; a word that might be a first name or initials is not on it). Every other address counts as a
  person's: `scrub.sql` gives each distinct one an invented `contact<N>@example.org` (N its rank, `guides.scrub_mail`
  src `deny`), the same way and in the same places as a person's address, and `english-history.mjs` in the snapshots;
  `check.sql` (also run again on the finished copy) and `english-history.mjs` fail the run when one is left.
- **Repository files** (`make-guides-home.sh`, since 2026-11-14; default-deny and placeholders since the third round
  the same day): a file of the guides home's `repo/` that holds an address default-deny does not keep (a person's
  address, an address of a person's form, or any other address outside example.org that is neither on the
  functional list nor made of role words only) does not reach the copy as it is, so the repository import never
  brings it in: a PDF becomes a one-page placeholder of the same name ("Example document. The original is left out
  of the guides' copy."), a file of any other kind is left out. It is read in its bytes, in a PDF's streams
  (inflated, ASCII85 or ASCIIHex decoded), a docx, xlsx or zip file's parts, the text pieces of a PDF's content
  streams joined the way a reader sees them, and `pdftotext`'s text when it is there; also URL-encoded or with the
  at-sign as an entity. The rows that name such a file stay: an attachment or a publication document that became a
  placeholder opens as the placeholder, and a file that was left out answers 404. No picture shows the content of
  one (a rendered page, a thumbnail, a size or a page count): the pictures of the one-off publication
  (`PublicationOneOffPage.png`, `PublicationPublicPeriodDialog.png`) show its rows, and its file is a placeholder;
  the PDF pictures draw reports the backend renders; the publish checklist reads the file path in the database
  only. A check fails the run when a file of the made home still holds such an address (`repo-files.mjs check`),
  and `repo-files.mjs check-db`, which `seed-examples.mjs` runs first, when a `RepoFile` row does or the table is
  empty.
- **Mail queue**: deleted (empty in `niord_test`).
- **Secrets**: password settings, the WMS login, the legacy database login, Twitter keys: emptied.
- **Not touched by the scrub** (`english.sql` and `english-history.mjs` change some of it afterwards, for the language,
  not for personal data):
  message content (published content is public; never-public texts are only counted) but for a person's address,
  the message history snapshots (message content with no user field; the history's user is the scrubbed `User` row;
  the exceptions are above), the script
  resources and their history (templates with the organisations' functional mailboxes), organisation names, sources,
  charts, areas, categories, publications, dictionaries.

## After a backend start

Since 2026-11-14 `niord_test` has Liquibase changesets 001 to 011, the ones `main` has, and so has the copy: the
`RepoFile` table is there and empty, and a backend of `main` starts on it with "Database is up to date". Attachments
and publication files answer 404 until a sysadmin runs the repo-import batch job once against the copied folder:
`POST /rest/batch/repo-import` with `{"dir": "<your home folder>/.niord-ng-guides/repo"}` (forward slashes).

Then, in the same backend run, the example rows (`seed-examples.mjs`, above; about 10 s, after the check below; the
amendment needs the publication files of the repository import, and the firing exercises it has the backend generate
last are there before any picture, whatever the hour). Since 2026-11-14 `seed-examples.mjs` first runs the check of
the imported files itself (`repo-files.mjs check-db`, about 5 minutes with `pdftotext`: it fails when a `RepoFile` row
holds an address default-deny does not keep, or when the table is empty) and stops, making nothing, when it fails;
nobody has to remember it:

```
node fe/guides-shots/data/seed-examples.mjs
```

The check can still be run alone: `node fe/guides-shots/data/repo-files.mjs check-db`.

The order on a new copy is: `make-guides-db.sh`, `make-guides-home.sh`, `start-rig.sh`, the repository import,
`seed-examples.mjs` (which runs `repo-files.mjs check-db` first and stops on a hit), then the pictures. `prepare.sql`
leaves `BatchData` empty, so the repository import is the backend's job instance 1. The batch engine keeps its runs in
memory, so after a restart of the rig the Batch Jobs page lists the runs since it, and the sysadmin manual's Batch Jobs
pictures start the runs they show again.
`make-guides-db.sh` also removes the guides home's `batch-jobs` folder: the job numbers start again on a new copy, and a
run would otherwise append its log to the file an earlier copy's run left there.

What needs a backend start to show: the template changes of `english.sql` (script resources are cached: the audio and
NAVTEX texts), the settings, dictionaries and promulgation types. The publication changes of `prepare.sql` and
`english.sql` (languages, desc rows, the removed issues, the audit reasons, the category description) are read per
request and show at once.
