Data, not code. Loaded only into a fresh deployment (bootstrap), only by a sysadmin's import (releases), or
only into the demo database (sample). A running deployment's data may differ from these files and is the
truth; nothing here ever changes it.

# The sample

The Danish sample deployment (`docs/fe-country-split-plan.md` R11 and P9; `docs/code-data-config-plan.md` §8,
kind (f)): Danish domains, series, charts, areas, publications and messages, so that a newcomer's Niord has
content after one command. It is loaded only into the loopback database `niord_sample`, by
`./start-local.sh --sample` (`be/niord/scripts/load-sample.sh`, with `psql`, after the base product's bootstrap),
or by a country's launcher into its `niord_sample_<cc>` after the same bootstrap on the country's backend, and
never from a class path, a jar or an image: `CoreResourcePackagingTest` checks niord-base's classes and
`be/k8s/scripts/check-no-sample.sh` the built jars, the bootstrap zip and the image inputs in CI (it reads jars,
zips and docker export tars, and refuses a docker save tar).

| Path | What | Made by |
|---|---|---|
| `archive/` | the sample's base data as a bootstrap archive (`batch-set.json`, its data files, `templates/`), applied by the regeneration as the second archive of one bootstrap run after the base product's `../bootstrap/` | copied (below) |
| `messages/messages.json` | the 34 sample messages, in the message import's format (`PagedSearchResultVo<SystemMessageVo>`) | written for the sample |
| `niord-sample.sql` | the rows the sample adds on top of the base product's bootstrap, the four attachment files among them as rows of the repository store (`RepoFile`), a `psql` script with its own guard: its own ids from 1,000,001, the base rows named by natural key | generated by `../scripts/regen-sample.sh`, never edited |

## Where the sources come from

- `archive/domains.json` (the five domains `niord-nw`, `niord-nm`, `niord-fa`, `niord-almanac` and
  `niord-annex`, with the six series `dma-nw`, `dma-nw-local`, `dma-nm`, `dma-fa`, `dma-nm-almanac` and
  `dma-nm-annex`), `archive/promulgation-types.json` (`NAVTEX`, `Audio` and `Twitter` with their domain links), and
  the four scripts `templates/mailinglist/fetch-firing-exercises.js` and `audio-broadcast.ftl` (named by the
  mailing lists) and `templates/tmpl/dgps.ftl` and `dgps.js` (named by the category Radio navigation/DGPS) are
  copied unchanged from `SIFA-DK/niord-dk`'s bootstrap, `be/bootstrap/` on `feature/p5-dk-moves` at `68b95cf`
  (DK's merged bootstrap after its #2–#4), as Danish sample content. One exception: since the country split's P7,
  the `Audio` entry of `archive/promulgation-types.json` restates the base product's `Audio` (English, priority 50)
  with its `niord-nw` link, as its `NAVTEX` and `Twitter` entries restate theirs. Within the bootstrap run a value
  this archive gives replaces the base product's (the owner's ruling of 2026-10-24), and a changed base row is what
  `../scripts/regen-sample.sh` refuses (it compares the base rows with those of a base-only run), so the sample restates
  the base values and only the link applies: a `da` here would replace the base product's English. Drift from DK's
  bootstrap is accepted, and nothing is fetched at run time. The domains are clients of the local realm, so the
  local users hold roles in them.
- The other archive files came from the demo archive `niord-dev-basedata.zip`, deleted in C4b (in git history),
  pretty-printed: `categories.json` (the base bootstrap's 45 categories, restated, to which the same-run rule adds
  their Danish descriptions and domain links, and to `Radio navigation`/`DGPS` the two scripts `tmpl/dgps.js` and
  `tmpl/dgps.ftl` and its `dgps` template parameter, which the base leaves out), `aton-dict.json` (115 entries with
  their Danish descriptions, the four DGPS stations included), `parameter-types.json` (34, none standard: the base bootstrap's 32 restated, whose 13 composite types gain their
  Danish names while the 19 list types restate the base's values equally, so their entries here change nothing; and
  `dgps` and `dgps_station_list`), `charts.json` (172), `areas.json` (55), `sources.json` (29),
  `publication-categories.json` (4), `publications.json` (8) and `mailing-lists.json` (5 definitions, all
  inactive, with no recipient). Changed from the zip: every `niord-client-*` domain id renamed `niord-*`, and every
  category's `messageId` removed (they named Danish messages the sample does not have); and, in the review of #192
  (2026-10-23), the zip's own defects mended: the last five sources' English descriptions paired with their own
  organisations again (SVN with RDN, TBST with TBST, VBC with NAVWEAPONCEN DNK, VD with VD, VFK with DC DNK), the
  space at the end of two source names and three chart names removed, the mailing lists' typos corrected, and the
  publications' six plain-http links to 2015 and 2016 documents left out; since the owner's ruling of 2026-11-03
  each of the three external link publications carries a stand-in address at `example.org` in their place, the
  sample's only domain, as for its e-mail addresses. There are no reports: DK's are DK's bootstrap.
- `messages/messages.json` was written for the sample on 2026-10-22: navigational warnings and notices to
  mariners in Danish waters, in every status, with geometry and four generated attachments, in English and Danish.
  The objects they describe are fictitious (`SAMPLE-1`, …), and every position lies at sea where the vicinity
  says (judged from general geography; nine were moved there in the review of #192, and two firing-area titles
  lost a doubled period). They are never exported from a Niord environment or a local import of one.

## The safety rules

P9's safety rules (security review, 2026-10-19), as `../scripts/regen-sample.sh` enforces them on every
regeneration and `SampleFolderTest` on every Backend CI run (`org.niord.test.sample.SampleSafetyCheck`, whose
javadoc states each rule exactly):

- `niord-sample.sql` holds only the statements the regeneration writes (`\set ON_ERROR_STOP on`, `BEGIN`,
  `COMMIT`, the guard as the first statement after `BEGIN` and writing nothing, `SET`, the triggers'
  `ALTER TABLE … DISABLE|ENABLE TRIGGER ALL`, one-row `INSERT`s and the sequences' `setval`), each on a table of
  the allow-list: no user, contact, comment, history, recipient, batch, setting, SECOM or issue row, and no other
  statement;
- the only e-mail domain is `example.org`, in the whole SQL and in the content of every `RepoFile` row that is not
  a PNG (an address with letters outside ASCII included);
- no string value of an `INSERT` holds a phone number in the forms checked: `+` or `00` with a country code and
  digits, eight digits in a row, eight digits grouped 2-2-2-2 by spaces, dots or dashes (`&nbsp;` and the no-break
  space read as spaces), and tlf/tel/phone followed by digits; identifier columns (uids, paths, MRNs) are not read;
- every message title, in every language, starts with "SAMPLE —";
- every `RepoFile` row lies at a path of the repository's layout and holds a PNG drawn by
  `org.niord.test.sample.SampleTool`, whose chunks are exactly IHDR, PLTE, IDAT and IEND: no metadata chunk, no
  colour profile, no other kind of file;
- the SQL carries a sentinel line, by which `check-no-sample.sh` recognises it in a jar, a zip or a docker export
  tar, beside the messages' uid prefix.

The loader refuses (`load-sample.sh`, exit 1) unless the database host is loopback, the database is `niord_sample`
or `niord_sample_<cc>` with a two-letter lower-case country code (both checked before any container is asked,
which `LoadSampleScriptTest` runs) and the `niord-db` container publishes its port on loopback only; it writes no
row when the sample is already loaded (exit 3); the attachment files are rows of the SQL, so nothing is copied.
`./start-local.sh --sample` calls it when the database does not hold the sample yet. The SQL's
own refusals are exercised by `SampleOnACountryBaseITTest` and the regeneration's schema check.
`./start-local.sh --sample --reset` drops `niord_sample` and nothing else, through the launcher library's
`sample_reset`, which refuses any name but `niord_sample` and `niord_sample_<cc>`. Mail goes to the loopback
MailHog, and SECOM's outbox dispatch is off.

## The sample users

The local realm (`be/keycloak/niord-realm-local.json`) has one user per role, each with the name as password:
`sysadmin`, `admin`, `editor` and `user` (`<name>@example.org`; on a realm imported before P9, only after
`docker compose -f be/docker-compose.yml rm -sf niord-keycloak && docker volume rm niord-keycloak-data` and a new
start, because Keycloak imports the realm file only when the realm does not exist yet). Their groups hold their
role in the five sample domains. The chart's realm gains none of them, and its own users are not the sample's.

## Languages

The sample carries English and Danish. The base product's settings offer English only, so the Danish texts show
once a sysadmin adds `da` to `modelLanguages` on the Settings page and reloads the page (the administration app
reads the languages when it loads). On a country's backend whose own settings name Danish (DK's), they show from
its first start.

## Regenerating

Run `be/niord/scripts/regen-sample.sh` (its header says how it works) after a change to the base product's
bootstrap, the schema (a Liquibase changeset), the entities or the sample's sources, and commit what it writes.
Two runs write the same bytes, on any day: the bookkeeping timestamps (`created`, `updated` and the mailing-list
triggers' `nextScheduledExecution`) hold the sample's epoch. `SampleTool` draws at most 99 attachments, labelled
"SAMPLE 1" to "SAMPLE 99" in the order `messages.json` names them.

The SQL loads on any country's backend after the base product's bootstrap: a country's first start writes its own
default texts before any bootstrap, so the base rows' ids differ from country to country, and the SQL never names
one. The sample's own rows take the ids from 1,000,001 on, in every table, and a reference to a base row is its
natural key, a subselect in one of five tables' shapes (`org.niord.test.sample.SampleReferences`): a dictionary by
name, a dictionary entry by its dictionary and key, a promulgation type by its typeId, a category by its MRN or,
without one, its English name, and a template parameter by its owner (a category, or a composite parameter type
by name), its position and its paramId. After the load every sequence the sample touched stands at or above its
highest id, so the backend hands out ids above the sample's.

The guard refuses a database the SQL does not fit, and names the remedy: unless the database is `niord_sample` or
`niord_sample_<cc>`, its schema is there and its bootstrap marker reads applied, its Liquibase changesets are the
ones the sample was made on, no table holds a row at or above 1,000,001 nor has its sequence there, the sample's
domains and message series are not there yet, and every base row the sample names, and every base parameter type
its template parameters name, resolves by its natural key to exactly one row. Liquibase changesets that differ: the
sample was made on another schema, and is regenerated. Any other refusal: the database is not one clean run of the
base product's bootstrap (an interrupted bootstrap, rows added since, or a country's archive posted beside the base
product's: a country's `--sample` posts the base archive only), and `./start-local.sh --sample --reset` recreates
it; the sample is regenerated only if the base product's bootstrap, schema or entities changed since it was made.
After a `git pull` that changes this folder, `--reset` loads the new sample.

`SampleFolderTest` fails in Backend CI on a sample that breaks the safety rules, on a guard whose changesets
differ from the changelog's (a new changeset needs a regeneration), on an id below 1,000,001 or a base row named
other than by natural key, on a bookkeeping timestamp that is not the epoch, on a link the import dropped (the rows
of the link tables against `messages.json`), and on the zip's defects coming back (a name with a space at an end, a
doubled period in a title, a link). A drift of the base product's bootstrap that the keys no longer resolve needs a
database, so it shows when the sample is loaded: in `SampleOnACountryBaseITTest` (the base bootstrap after a
country-like first start), in the regeneration's schema check and in the IT fixture's regeneration.

## A local trial only

Keycloak runs in development mode and the passwords are known: never expose the sample deployment beyond this
machine. A country deploys with the chart (`be/k8s/helm/niord`), and its fresh deployment gets its data from the
bootstrap command, never from the sample.
